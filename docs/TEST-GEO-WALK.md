# Geo/Walk: ручная проверка GPS-прибытия и ETA

## Подготовка

1. Запустите backend и debug-приложение. Для локального backend настройте `adb reverse tcp:8000 tcp:8000`.
2. Создайте московский маршрут с началом около МХТ и первой точкой «Большой театр».
3. Возьмите **точные** `lat` и `lon` первой точки из ответа `POST /v1/routes`, а не координаты,
   найденные по названию здания.
4. Очистите Logcat и начните сбор диагностики:

   ```powershell
   adb logcat -c
   adb logcat -v time GulyayGeoWalk:D GulyayNetwork:I AndroidRuntime:E *:S
   ```

Координаты печатаются тегом `GulyayGeoWalk` только в debug-сборке.

## Основной сценарий

1. До запуска прогулки проверьте время пешком от стартовой позиции до первой точки.
2. Запустите прогулку. Убедитесь, что подсказка относится к первой точке, а ETA не включает
   остаток всего маршрута.
3. В Android Emulator → Extended controls → Location задайте точные `lat`/`lon` первой точки
   из ответа API и отправьте позицию один раз.
4. Не перемещайте GPS. Первое допустимое измерение не должно отметить точку; интерфейс должен
   показать «Вы у точки»/«Точка маршрута рядом» и ожидание повторного GPS-измерения.
5. Приложение запрашивает свежее повторное измерение не ранее чем через 5 секунд. Если два
   серверных слота текущей скользящей минуты уже использованы, оно показывает cooldown и ждёт
   освобождения окна — максимум около 60 секунд, либо срок из `Retry-After` при HTTP 429.
6. После второго свежего измерения с точностью не хуже 50 м backend должен вернуть
   `pointReached=true`, `phase=VISITING`; `currentPointOrder` не меняется. Секундомер начинается
   с `00:00` и считает вверх.
7. Оставьте GPS внутри 75 м: прогулка остаётся в `VISITING`, секундомер продолжает идти.
8. Отправьте одну точную позицию дальше 115 м: это ещё не завершает посещение. Верните GPS внутрь
   115 м и убедитесь, что случайный выход сброшен.
9. Снова отправьте позицию дальше 115 м дважды с интервалом не меньше 5 секунд. Из-за скользящего
   лимита второй запрос может ждать освобождения серверного слота. После подтверждения backend
   возвращает `pointExited=true`: для промежуточной точки включается `MOVING` и увеличивается
   `currentPointOrder`, для последней прогулка становится `COMPLETED`.

Ожидаемые логи: provider, возраст и точность измерения, номер и расстояние до текущей точки,
причина отправки/пропуска, затем backend-ответ с `pointReached`, `pointExited`, `phase`,
`visitElapsedSeconds` и `currentPointOrder`.

## Дополнительные проверки

- Установите accuracy хуже 50 м: точка не подтверждается, UI сообщает о недостаточной точности,
  запрос не расходует клиентский слот.
- Поставьте прогулку на паузу: новые позиции не отправляются и точка не подтверждается.
- Поставьте на паузу во время `VISITING`: секундомер должен замереть. После `RESUME` отсчёт
  продолжается без включения времени паузы.
- Закройте процесс приложения во время `VISITING`, откройте маршрут снова: backend возвращает
  ту же точку, фазу и фактическое время; секундомер продолжается с восстановленного значения.
- Остановите прогулку: последующие GPS-события не возобновляют её.
- Временно отключите backend: состояние прогулки сохраняется; после восстановления сети новые
  свежие измерения снова обрабатываются.
- На маршруте с петлёй/пересечением пройдите один участок последовательно: ETA не должен
  перескакивать на другой leg или резко расти при приближении к текущей точке.
- Для проверки transient offline очистите Logcat, откройте маршрут и кратковременно оборвите
  первый `GET /v1/routes/{id}`. В журнале должны быть максимум две попытки. Если повтор успешен,
  офлайн-экран не появляется. При двух сетевых отказах открывается только read-only snapshot;
  кнопки запуска и изменения прогулки скрыты. HTTP 404/ошибка доступа не маскируются snapshot.

Для фиксации backend-ответов можно параллельно сохранить журнал uvicorn. HTTP 400/409/429 также
видны по тегу `GulyayNetwork`; `GulyayGeoWalk` показывает соответствующий `error` и cooldown.
